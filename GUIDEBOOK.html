Shopee AI Commerce Agent

A conversational commerce agent for buyers and sellers — with an approval queue, a strict state machine, AI orchestration, WhatsApp integration and a deployment-ready stack. An LLM that never executes anything without you.

6 / 6 phases complete 141 / 141 tests passing 10 acceptance tests ✅ WhatsApp hardened Deployment-ready

1. Overview

ShopBot is a commerce assistant that works in two modes:

🛒 Buyer

Search a catalog, compare products, place orders, track order status. Every order becomes a proposal that waits for your explicit approval.

🏪 Seller

Draft listings, publish after approval, check stock, get sales summaries. Publishing is an approval-gated execution.

💬 WhatsApp

The same agent on WhatsApp: Meta webhook verification, signature checks, retry dedup, and interactive Approve / Reject buttons.

🧠 AI orchestration

LangGraph state machine per user thread + Ollama for structured intent extraction, with a deterministic rule-based fallback that is always audited.

The core idea: the agent can read and prepare, but it can never execute. Execution happens only through the approval-bound executor, with revalidation and idempotency on every call.

3. Architecture

State machine (every consequential action)

REQUESTED→ VALIDATED→ PENDING_APPROVAL→ APPROVED→ REVALIDATED→ EXECUTING→ SUCCEEDED

Branches: PENDING_APPROVAL → REJECTED · EXECUTING → FAILED · EXECUTING → UNKNOWN → (SUCCEEDED | FAILED) via a status check — never a blind retry. Read-only actions skip approval entirely.

Persistence

SQLAlchemy 2.0 models: users, sessions, proposals, approvals, orders, listings, executions (unique idempotency key), audit_events, wa_messages (webhook dedup). Two Alembic revisions; SQLite by default, PostgreSQL in production compose.

4. Features

Buyer flow

  • Search with budget filters — find wireless earbuds under PKR 2,000 (≤3 results, all within budget).
  • Buy — buy the first one resolves against the last search and creates a proposal (never an order directly).
  • Approve / Reject — dashboard buttons or WhatsApp button taps; approving twice creates exactly one order.
  • Track — order status, including UNKNOWN → status-check resolution after a simulated marketplace timeout.

Seller flow

  • List — list a wireless earbud at PKR 1500 with stock of 10; missing fields get a correction request.
  • Publish — approval-gated; without an authorized marketplace integration the listing stays a local draft and you are told honestly.
  • Stock check & sales summary — read-only, no approval needed.

WhatsApp (Phase 4 + hardening)

  • Meta verification handshake (hub.mode=verify) and X-Hub-Signature-256 HMAC-SHA256 verification (enforced when an app secret is configured).
  • Session mapping: the E.164 phone number is the orchestrator user id (auto-provisioned).
  • Approval proposals arrive as interactive messages with Approve / Reject buttons; taps resume the paused LangGraph thread. Ownership is enforced — another phone cannot approve your proposal.
  • Hardening: at-most-once dedup by wamid (Meta retries never double-process) and ack-200-then-send-async (the endpoint returns immediately; replies go out in a background task).

AI orchestration (Phase 3)

  • One LangGraph thread per user; nodes: extract_intent → agent → (await_approval | END).
  • Ollama extracts intents as structured Pydantic output (format="json", temperature 0); a deterministic rule-based extractor is the audited fallback (llm_fallback events).
  • Human-in-the-loop: the thread interrupts at PENDING_APPROVAL; the next message resumes it (approve → executor, reject → cancel, anything else → fresh intent).
  • Persistent checkpointer (SQLite): paused approvals survive process restarts.

5. Safety & trust model

Non-negotiable invariants — implemented and tested:
  1. The agent/LLM never touches the DB or marketplace directly — only typed tools from a registry with levels READPREPAREEXECUTE.
  2. EXECUTE tools (place order, publish listing) are callable only by the executor after a valid approval — the agent cannot call them.
  3. Approvals are bound to proposal_id + proposal_version + user_id + payload_hash; any change to price/quantity/seller/shipping invalidates the approval.
  4. Permissions, price, stock, spending limit, marketplace rules and integration availability are revalidated before every execution.
  5. Every execution carries an idempotency key (persistent executions table); on timeout the outcome is UNKNOWN → status check, never a blind retry.
  6. Secrets live only in backend env/secret storage — never in prompts, logs or the browser (API keys shown once; only sha256 stored; /auth/me never exposes hashes).
  7. No scraping, no bypassing marketplace rules — official APIs only.
  8. Customer messages, product titles, reviews and descriptions are untrusted data, never instructions (prompt-injection defence; product cards strip descriptions).
  9. An audit event is recorded for every intent, proposal, approval, rejection, execution, error, WhatsApp in/out/button/duplicate and signature rejection.
  10. Per-user spending limits, rate limits (agent-level + HTTP-level) and max quantity per order.
  11. Real marketplace outcomes are reported; unverified success is never claimed.

9. Deployment & operations

Probes & metrics

  • GET /health/live — process is up.
  • GET /health/ready — database answers (503 when down).
  • GET /metrics — JSON snapshot: request counters by status, avg latency, rate-limit hits, 5xx, uptime + DB aggregates (proposals/orders/listings by status, audit events by type, executions).

Hardening (Phase 6)

  • Rate limiting: per-principal (API key / IP) sliding window, SHOPEE_RATE_LIMIT_PER_MINUTE (default 30) → 429 + Retry-After.
  • Security headers on every response: nosniff, DENY framing, no-referrer, CSP; CORS allow-list (never *).
  • Docker: non-root appuser, HEALTHCHECK → /health/ready, restart policies, resource limits.
  • Production overlay: Caddy reverse proxy (automatic HTTPS), backend/dashboard publish no ports, secrets from the environment, backup sidecar (pg_dump every 24h, 7-day retention).
  • Backups: scripts/backup_db.sh backup|restore (SQLite online backup + PostgreSQL pg_dump/pg_restore).

11. Troubleshooting & FAQ

"Something went wrong on my side" in chat

Check the error audit event for the user (or server logs). The orchestrator catches and audits every failure — nothing fails silently.

Approve says "no authorised marketplace integration"

Expected with SHOPEE_CLIENT=official and no credentials, or with an unauthorized WhatsApp client. The proposal stays pending / the listing stays a local draft, and an integration_unavailable event is audited.

Webhook returns 403

Either the hub verify token is wrong (GET) or the X-Hub-Signature-256 signature doesn't match SHOPEE_WHATSAPP_APP_SECRET (POST). A wa_signature_rejected event is audited.

Webhook returns 429

HTTP rate limit (per phone/IP, 30/min default). Meta retries are safe: dedup by wamid guarantees at-most-once processing.

Tests fail after a fresh clone

Run pip install -r requirements.txt first. The suite uses a temp SQLite DB and the rule-based LLM provider — no external services needed.

Does the approval survive a server restart?

Yes — the LangGraph checkpointer is persistent (SQLite). Live-verified: pause at PENDING_APPROVAL, restart the process, tap Approve → the order executes exactly once.

Can I use a real Shopee account?

Only an approved seller/ISV account in a supported market (Shopee has no Pakistan marketplace). Buyer-side automated ordering is not an official API — that flow stays on the mock client by design.

12. Roadmap (open items)

  1. Auth upgrade — JWT access/refresh tokens (or OAuth) instead of single-show API keys.
  2. Multi-worker scaling — Redis-backed shared rate limiter + Postgres checkpointer.
  3. LLM-written replies — LLM-generated reply text with the templates as audited fallback.
  4. WhatsApp account linking (WA users ↔ dashboard accounts); 24-hour-window handling improvements.
  5. Shopee deployment-time items (once real credentials exist): currency conversion, access-token refresh loop, weight/dimensions/images mapping.
  6. Infra: WAF/DDoS fronting (Cloudflare / cloud LB), durable outbox for WhatsApp sends, scheduled purge_old_wa_messages.
